## 2. Findings

### P0 — risque de plantage réel

**P0-1 [CORRIGÉ] Aucun timeout sur les ~20 fetch Microsoft Graph** — `graph-auth.ts`, `graph-mail-ingestion.ts`, `graph-mail-outbound.ts`, `graph-mailbox.ts`, `graph-calendrier-outbound.ts`.
Scénario : Graph (ou login.microsoftonline.com) hang → la server action reste bloquée jusqu'au timeout plateforme (minutes). Le gestionnaire voit un spinner infini, re-clique « Envoyer » → **double envoi de mail** possible. Fix : helper `graphFetch` dans `graph-auth.ts` — timeout systématique (30 s, env `GRAPH_TIMEOUT_MS` ; 60 s pour les PJ multi-Mo ; 8 s pour getSchedule qui dégrade en « inconnu ») + 1 retry sur 429/5xx **pour les GET uniquement** (les écritures ne sont jamais rejouées : doublon). Testé (`graph-auth.test.ts`).

**P0-2 [CORRIGÉ] Aucun timeout sur le tri IA des mails** — `mistral-analyse-provider.ts:92`.
Scénario : un appel Mistral qui traîne bloque la synchro ~300 s (HeadersTimeout undici) **par mail** ; avec 80 mails à analyser, la synchro ne rend jamais la main. Fix : `AbortSignal.timeout(60 s)` + retry des erreurs réseau (ECONNRESET comptait comme échec définitif alors que le catch de `synchroniser.ts` dégradait le mail sans le mettre en cache — désormais 1-4 retries avant). Même fix sur l'extraction patrimoine Mistral (180 s).

**P0-3 [CORRIGÉ] Routes d'analyse reprise sans `maxDuration` Vercel** — `app/api/reprise/analyser/route.ts`, `app/api/reprise/mapping-analyser/route.ts`.
Scénario : sur Vercel, la fonction est coupée à la durée par défaut du plan (~10-15 s) alors qu'une extraction IA dure de 30 s à plusieurs minutes → 504 en plein vol, crédit IA brûlé pour rien, le gestionnaire ré-uploade (double coût). Fix : `export const maxDuration = 300` (plafond Fluid compute ; si le déploiement échoue sur le plan de la collègue, redescendre à 60). Finding déjà repéré par l'audit pré-prod, désormais réglé.

**P0-4 [RECO] Mutations eStale composées non idempotentes** — `estale-assemblee-provider.ts` (`appliquerOdj` : N suppressions + M créations + 1 réordonnancement, séquentielles) ; même motif sur l'injection reprise (`estale-ecriture/reel-provider.ts`, orchestrée par le service).
Scénario : un 502 au milieu d'`appliquerOdj` laisse l'AG **à moitié modifiée** ; le gestionnaire re-clique → motions en double. Le client fait déjà le bon choix (jamais de retry auto d'une mutation), mais rien ne protège du re-clic humain. Reco : (a) désactiver le bouton pendant l'action + message « vérifier l'ODJ dans eStale avant de relancer », (b) à terme, rendre `appliquerOdj` reprenable : relire l'AG au début et ne créer que ce qui manque (réconciliation, comme fait pour l'ordre). Effort : (a) minime, (b) ~½ journée. Pas codé : logique métier sensible, à valider avec Sekou.

### P1 — coût évitable significatif

**P1-1 [CORRIGÉ] Le tri IA envoyait le corps de mail complet** — `mistral-analyse-provider.ts`.
`cleanBody` coupe l'historique cité, mais une newsletter/un dump de 30 000 caractères partait entier (~7 500 tokens) pour une simple classification. Fix : troncature à **2 000 caractères pour le tri** (~500 tokens, suffisant pour classer) et **6 000 pour la génération de réponse**, avec marqueur explicite pour le modèle (env `MISTRAL_MAX_CORPS_TRI` / `_PLAN`). Économie : sur les mails longs, −60 à −90 % de tokens d'entrée ; le prompt système (~800 tokens) devient le coût dominant, stable. Testé.

**P1-2 [CORRIGÉ] Chaque PDF patrimoine était OCRisé deux fois** — `mistral-extraction-provider.ts`.
`extrairePatrimoine` et `extraireProprietaires` tournent en parallèle sur les **mêmes** documents (orchestrateur, `Promise.all`) et chacun refaisait `ocrTous(docs)`. L'OCR Mistral est facturé à la page : un RCP de 100 pages = 200 pages OCR facturées au lieu de 100. Fix : dédup par WeakMap sur l'objet document (mémorise la *promesse* → dédoublonne aussi les appels en vol ; un échec n'est pas mémorisé). **−50 % du coût OCR par analyse.** Testé.

**P1-3 [CORRIGÉ] Liste complète des condos eStale refetchée à chaque geste ODJ** — `estale-assemblee-provider.ts`.
`getAssemblee`, `creerAssemblee` et `appliquerOdj` refaisaient chacun la query `me.collaborator.condos` (264+ copros) ; un « appliquer l'ODJ » en déclenchait jusqu'à 2-3 dans la même action. Fix : cache module TTL 10 min (même pattern que `estale-condo-provider`), et `creerAssemblee` ne demande plus que `collaborator.id`. Testé (`estale-assemblee-provider.test.ts`).

**P1-4 [CORRIGÉ] Énumération de toute l'arborescence de la boîte à chaque classement de mail** — `graph-mailbox.ts`.
`classerDansCopro` listait tous les sous-dossiers inbox (100/page, 2 niveaux — une boîte organisée par copro = plusieurs requêtes paginées) à chaque mail classé. Fix : cache par boîte TTL 10 min, **uniquement** pour le chemin automatique ; le picker (`listerDossiers`) reste live pour voir un dossier fraîchement créé.

**P1-5 [CORRIGÉ] Signature Signitic refetchée à chaque envoi** — `signitic-signature-provider.ts`.
Un GET par mail envoyé pour un HTML qui ne change presque jamais, sans timeout. Fix : cache TTL 15 min par email (succès seulement : un 404/panne se retente à l'envoi suivant) + timeout 10 s. Testé.

**P1-6 [RECO] Rafale getSchedule dans l'éditeur de date** — `components/fiche-copro/editeur-date.tsx:185-230`.
Trois `useEffect` déclenchent chacun une server action (→ getSchedule Graph) à **chaque changement** de date/heure/salle, sans debounce : régler une heure au clavier peut tirer 6-10 appels Graph en quelques secondes. Le timeout 8 s ajouté borne la casse, mais reco : debounce 400-600 ms sur `cleDispo`/`cleZoe`/`cleAgenda` (fichier UI, hors périmètre de fixes adapters). Effort : 1 h.

**P1-7 [RECO] La route d'analyse réécrit 5× la ligne dossier complète (JSONB `jeu` inclus)** — `app/api/reprise/analyser/route.ts:94-123` + `lib/reprise/services/suivi-dossier.ts`.
`appliquerRecap`, `enregistrerComptaResume`, `enregistrerComptaErreur`, `enregistrerJeu`, `ajouterJournal` font chacun `obtenir()` (SELECT *) puis `sauver()` (upsert **de toute la ligne**, y compris `jeu` qui peut peser plusieurs Mo pour un gros dossier) → jusqu'à 10 allers-retours Supabase lourds par analyse, avec risque de lost-update entre les cycles. Reco : une fonction de service « appliquer le résultat d'analyse » qui fait 1 lecture + 1 écriture ; ou un `sauver` partiel (colonnes ciblées). Effort : ½ journée. Pas codé : le service vient d'être restructuré, à faire à froid.

**P1-8 [RECO] Plafond d'upload (40 Mo) au-dessus de ce que les API acceptent réellement**.
- API Anthropic : **32 Mo par requête** et le base64 gonfle de ×1,37 → au-delà d'~23 Mo de PDF envoyés à une mission, l'appel échoue (413) *après* l'upload complet et l'attente.
- `claude-haiku-4-5` (mission propriétaires) a un contexte 200K → PDF plafonné à **100 pages** côté API ; un RCP de 150 pages échoue sur cette mission.
- Mistral (data-url) a ses propres plafonds du même ordre.
Scénario : le gestionnaire uploade 38 Mo, tout passe la garde de la route, l'extraction plante avec un message API brut. Reco : abaisser le plafond à ~20 Mo (ou vérifier par mission), et intercepter 413/« too large » avec un message actionnable (« scinde le PDF »). Effort : 1-2 h.

### P2 — hygiène

**P2-1 [RECO]** `claude-cli-*` : `spawn(BIN, args, { shell: true })` sous Windows — le kill au timeout tue le shell mais pas forcément l'enfant `claude` (process orphelin possible) ; et `shell: true` est fragile si `CLAUDE_CLI_BIN` contient des espaces. Adapter réservé aux tests locaux, risque accepté ; si utilisé davantage : `taskkill /T` ou `tree-kill`.
**P2-2 [RECO]** Login eStale concurrent : deux requêtes qui prennent un 401 en même temps déclenchent deux logins (pas de mutex). Sans conséquence (le dernier cookie gagne), coût marginal.
**P2-3 [RECO]** Les messages d'erreur des adapters embarquent `(await r.text()).slice(0, 200)` : bien borné, pas de corps de requête (donc pas de PII sortante) — garder ce réflexe.
**P2-4 [RECO]** La suite vitest contient des tests « smoke » qui font de **vrais appels eStale** (`smoke-mapping.test.ts`, ~35 s, dépend des credentials) : à isoler derrière un flag/env pour que `vitest run` reste hermétique en CI.
**P2-5 [RECO]** `supabase-mes-emails-etat-repository.getEtats` fait `select("*")` sans limite — table par gestionnaire, volume faible aujourd'hui ; passer aux colonnes explicites à l'occasion.
**P2-6 [OK]** PII : les corps de mails partent chez Mistral (choix RGPD assumé : Mistral EU, documenté) ; les variables GraphQL eStale sont expurgées des logs ; aucun secret en dur trouvé ; les clés viennent toutes de l'env.
**P2-7 [OK]** Modèles bien dimensionnés : tri mail sur `mistral-small` (pas large), spec compta sur small, patrimoine Claude routé sonnet (structure) / haiku (transcription). La compta est passée en couche texte pure (zéro IA) — meilleure décision coût/fiabilité de tout le module.

## 3. Section dédiée : chaîne d'ingestion/analyse reprise (bout en bout)

**Routes upload** (`/api/reprise/analyser`, `/api/reprise/mapping-analyser`) : garde de taille AVANT lecture (somme des `f.size`, gratuit), lecture séquentielle en RAM (lisse le pic ; 40 Mo max + base64 transitoire ≈ pic ~150 Mo par requête — acceptable sur Vercel 1-3 Go, mais deux analyses simultanées se cumulent), auth session, erreurs JSON propres. Manquait `maxDuration` (P0-3, corrigé). Si le client abandonne (fermeture d'onglet), Next/Vercel n'annule pas le travail : l'extraction va au bout et le résultat est quand même persisté côté dossier (`enregistrerJeu`) — donc pas de crédit entièrement perdu pour `analyser` ; pour `mapping-analyser` (rien de persisté à part les décisions), le travail est perdu — comportement acceptable, à savoir.

**Extraction patrimoine** : les PDF partent **entiers** en base64 dans chaque mission (2 missions). C'est le choix assumé (Claude lit les PDF nativement, évite pdf.js côté patrimoine) mais c'est le poste de coût principal — voir estimation §4 et P1-8 pour les plafonds. Mistral : OCR maintenant dédupliqué (P1-2), timeout posé. **Pas de cache d'analyse** : ré-analyser le même dossier repaye tout ; le jeu étant persisté (JSONB `jeu`) et réhydraté à l'ouverture, la ré-analyse n'arrive que sur geste explicite — un hash des documents pour court-circuiter une ré-analyse identique serait un plus, pas une priorité.

**Rate limits** : throttle 1,2 s/appel (tri mail + patrimoine Mistral), backoff avec `retry-after` honoré, 8 tentatives côté compta (fenêtre par minute documentée dans l'historique du projet). Le pipeline patrimoine fait seulement 1 OCR + 2 chats par analyse : sous les paliers bas.

**Claude CLI** : timeout 300 s + kill (voir P2-1), fichiers temp nettoyés en `finally`, clés API retirées de l'env du sous-processus (session Max voulue). Réservé aux tests, OK.

**Couche texte (pdfjs)** : aucun réseau. Import dynamique du build legacy sans worker (compatible serverless), `doc.destroy()` en `finally`, copie défensive du buffer. Charge mémoire ≈ le PDF + items texte (raisonnable). Les erreurs ne sont **pas** avalées : fallback OCR *visible* (note dans le jeu + console.error) — bon pattern.

**Persistance** : le jeu JSONB repart entier à chaque `sauver()` — voir P1-7. La liste des dossiers exclut `jeu` du SELECT (bien) ; `obtenir()` le charge (nécessaire).

## 4. Estimation des coûts par geste

Ordres de grandeur, à recaler sur les factures réelles (tarifs Anthropic vérifiés : sonnet-4-6 = 3 $/M tokens entrée, 15 $/M sortie ; haiku-4-5 = 1 $/5 $. Tarifs Mistral non vérifiés ici : raisonner en volumes).

**Tri d'un mail (Mistral small)** : prompt système ~800 tokens + en-têtes + corps tronqué ≤ ~500 tokens ≈ **~1 400 tokens d'entrée, ~80 de sortie** par mail analysé. Une synchro de 80 mails dont 30 nouveaux « pass » ≈ 45 000 tokens d'entrée — quelques centimes sur small, et le cache fait que ça ne se repaye jamais. Avant troncature, un seul mail-fleuve pouvait coûter autant que 15 mails normaux.

**Brouillon de réponse (à la demande)** : ~1 000 (système) + ≤ 1 500 (corps 6 000 car.) tokens d'entrée, ~250 de sortie. Généré seulement à l'ouverture du mail (décision déjà en place, bonne).

**Analyse patrimoine via Claude** (PDF ~30 pages, ~5 Mo) : un PDF compte ~1 500-3 000 tokens/page (texte + vision). 30 pages ≈ 45-90K tokens, envoyés **2×** (sonnet + haiku) → entrée ≈ 0,15-0,30 $ (sonnet) + 0,05-0,10 $ (haiku), sorties ≤ 16K tokens ≈ 0,10-0,25 $. **≈ 0,3-0,7 $ par analyse** ; un gros dossier 100 pages/20 Mo ≈ **1-2 $** (et bute sur les plafonds, cf. P1-8).

**Analyse patrimoine via Mistral** : OCR facturé à la page (1× désormais, était 2×) + 2 extractions `mistral-large` sur le markdown OCR (≈ 0,5-1K tokens/page ×2 missions). Volume dominant = l'extraction large ; pour économiser : `MODEL_EXTRACTION=mistral-medium-latest` à essayer, les auto-checks aval rattrapent.

**Grand livre (mapping compta)** : **0 € d'IA** (couche texte pure) — seuls des appels eStale de lecture. Le fallback OCR/full-LLM n'existe plus dans le routeur compta.

**Fiche copro (eStale)** : 5-6 queries GraphQL, servies du cache 20 min après la 1re ouverture — sain.
